# Context

Project context for LLM agents working on this codebase. README.md is the operator guide (configure, run locally), DEPLOY.md is the server-install guide. This file describes how the system is built and why decisions were made, plus the durable parsing and tooling facts learned while building it. It contains nothing about the actual game data or analysis findings; those are recomputed live from the database by the LLM.

## Everything Runs in Containers

There is no host build or host run path. The Go binary, the Rust sidecar, and `sqlc` all run inside Docker, against the repo bind-mounted at `/sources`. `make` targets are thin wrappers over `docker compose`. The app is operated only through Compose; there is no expectation that Go, Rust, or sqlc are installed on the host (they are only needed if you want host-side tooling such as gopls).

## Architecture

Two binaries plus Postgres.

- `main` (Go CLI and server, module `main`): ingests replays and serves the web UI. Talks to Postgres via pgx/v5 and pgxpool. Queries are generated by sqlc into the `models/` package (gitignored, regenerated with `make sqlc` or in-container on startup).
- `sc2json` (Rust sidecar, `sidecar/`): parses one .SC2Replay into compact JSON on stdout, built on s2protocol-rs. Stateless, one replay per invocation. Baked into the image at `/usr/local/bin/sc2json`; the Go side finds it via the `SC2JSON` env var.
- Postgres: single account, single `public` schema, holds both the game tables and the chat tables.

`main` has four actions: `ingest`, `serve`, `statistics` (row counts per table), and `sample` (pretty-print the sidecar JSON for one replay). The earlier precomputed analysis reports were removed; all analysis is now done live by the LLM in the web UI.

## Ingest Pipeline

`main -action ingest` walks the `REPLAYS` directories recursively for .SC2Replay files, skips any path already in the `files` table (any status, never retried), and runs the rest through a worker pool (`WORKERS`, default CPU count, CPU-bound). Each file ends in exactly one state:

- `duplicate`: a copy of an already-imported match. Matches are deduplicated by a SHA-256 fingerprint of played_at, map, and the team:name roster, so the same game saved under several paths is stored once.
- `failed`: the sidecar could not parse it. Delete the `files` row to retry.
- `imported`: parsed and stored in one transaction (game, players, messages, stats, units).
- `skipped_ai`: the game has a Computer participant; only player-vs-player games are stored.

Re-running ingest is cheap (already-processed paths are skipped without touching the replay). To re-import after a parser change, bump `PARSER_VERSION` in `sidecar/src/main.rs` and run `docker compose run --rm cli -action ingest -force`.

## Data Model

`files` records every path seen with its status and parser version. `games` (one per imported file, fingerprint-unique) -> `players` (team is a column; there is no teams table) -> `messages`, `stats`, `units` keyed by `player_id` and `tick` (game loop). The `matches` view joins winners and losers per game; the model can query it directly.

Units semantics (the `action` column):

- `born`: units created instantly (trained, hatched), owned by the player.
- `init`: construction or warp-in starts (buildings, warped units), owned by the player. Cannons and other buildings only ever appear here.
- `killed`: credited to the killing player (a row means "kill by this player"). Deaths without a killer are not stored.

Engine helper units (for example InvisibleTargetDummy) are filtered out in the sidecar.

Durable facts needed to write correct SQL (full list under Replay Format and Parsing below): tick = 1/16 in-game second (960 per in-game minute); `tick / 16` lines up with `games.duration` (in-game seconds); PlayerStats arrive every 160 ticks; `food_used >= 195` means maxed; `food_used` and `food_made` are already real supply values.

## Replay Format and Parsing

- Tick = game loop. 16 loops per in-game second, 960 per in-game minute. `games.duration` is in-game seconds, so `tick / 16` lines up with duration. PlayerStats events arrive every 160 ticks (10 in-game seconds).
- `UnitBorn` = instantly created units (trained, hatched). `UnitInit` = construction/warp-in starts (all buildings, warpgate units). Both are needed: cannons and other buildings only ever appear as `UnitInit`. `UnitDied` carries `killer_player_id`; deaths without a killer (expired, suicide) are dropped by design.
- The game-end PlayerStats snapshot reuses the last periodic tick - the sidecar keeps the later event, or the stats PK `(player_id, tick)` would reject it.
- `InvisibleTargetDummy` (and other `*Dummy*` units) are engine helpers spawned per ability attack - thousands per game, born and instantly killed. Filtered in the sidecar; without the filter one player showed 15421 units instead of 1223.
- Lobby slot control values: Human = 2, Computer = 3 (AI players are named like "A.I. 2 (Hard)"). Participants have `observe = 0`.
- Player identity: details names embed clans as `&lt;CLAN&gt;<sp/>Name`; init-data has bare `name` + `clan_tag`, but with stray NUL bytes that must be stripped. MMR is init-data `scaled_rating`; APM/races/result/duration/version come from `replay.gamemetadata.json` (plain JSON in the MPQ, readable for any protocol version). Mode flags (`amm`, `competitive`) are in init-data game options.
- Tracker player_id maps to players via PlayerSetup events (player_id -> user_id + slot_id) and details `working_set_slot_id`. Never use lobby slot order (v1's attribution bug).
- s2protocol-rs falls back to the nearest known protocol for unknown base builds - parsed every replay from 2022 through build 96883 (2026) with zero errors. Blizzard's Python s2protocol and icza/s2prot stopped at protocol 95299 (Oct 2025) and fail on current replays.
- `food_used`/`food_made` are already divided by 4096 in s2protocol-rs (real supply values).
- gamemetadata races are 4-char codes (`Terr`, `Prot`, `Rand`); the sidecar normalizes to full names.

## Tooling Quirks

- A Go module named `main` cannot run `go test` (the test binary cannot import package "main"). Fine here since tests were removed by choice.
- sqlc (verified through v1.31.1) cannot propagate aggregate-alias columns out of CTEs and gets confused by unqualified `name` in multi-CTE queries ("column reference is ambiguous"). Qualify columns (`players.name`) when writing new queries.
- Parser changes: bump `PARSER_VERSION` in `sidecar/src/main.rs`, then `docker compose run --rm cli -action ingest -force`.

## Web UI: One Agentic Tool Loop

`main -action serve` starts a web page where anyone can ask questions about the database in plain English and get a written answer. A browser cannot hold the OpenRouter key or open a Postgres connection on a public page, so the three static frontend files are served by the Go binary, which holds the key, talks to Postgres, and exposes a small JSON API.

This is the Claude Code model, not a fixed pipeline. There is one conversation thread and the AI has exactly one tool: `run_sql(query)`.

1. The system prompt tells the model: you answer questions about this StarCraft 2 replay database, here is the schema, here are the domain rules, you have a `run_sql` tool, give your final answer in markdown.
2. The user asks a question.
3. The model emits a tool call: the SQL it wants to run.
4. The server executes it (read-only transaction, 30s statement timeout) and returns the rows to the model as the tool result.
5. The model reads the rows and either calls `run_sql` again (to fix an error or drill further) or writes its final markdown answer.
6. The server renders that answer to HTML and shows it.

What falls out of this design:

- Continuation is just chat. The conversation is a normal message list that we resend each turn.
- No separate summarizer. The same model that ran the query writes the answer in the same thread, so the answer is grounded in the rows it actually saw.
- Retry is automatic. If a query errors, the Postgres error comes back as the tool result and the model corrects itself and re-runs. No special retry code.

The model is forced to run at least one query per question (the first model step requires a tool call), so it can never answer a data question from memory. After that it is free to stop and answer or run more, up to a cap of 3 `run_sql` calls per question; past the cap it must answer with what it has or report that it could not.

## System Prompt

The system prompt is rebuilt on every call (not stored), so schema or rule changes take effect immediately, even in old chats. It embeds:

- The key durable domain facts the model needs to write correct SQL (see Replay Format and Parsing above): tick math, `food_used >= 195` means maxed, unit `action` semantics, team is a column (no teams table), the `matches` view, and the tracked PLAYERS.
- The full schema, via `go:embed sqlc/schema.sql`. The whole schema is shown, including the `conversations` and `turns` tables; the prompt simply tells the model those hold the chat app's own history and to ignore them for game questions. (There is no clever trimming; reads are read-only anyway, and the app is public by choice.)

Only durable facts go in. Precomputed analysis findings are deliberately left out, so every answer is recomputed from live data. The prompt also tells the model to use Postgres `now()` and `current_date` for relative dates, so today's date never has to be injected.

Answer style (instructed in the prompt): answer-first and concise; use markdown tables whenever a query returns multiple rows; always cite the sample size ("over N games"); never speculate beyond the rows returned; and when a query returns nothing, say so plainly.

## AI Provider and Model

- Provider is OpenRouter (OpenAI-compatible chat completions with tool calling), called over plain `net/http`. No SDK.
- Endpoint `https://openrouter.ai/api/v1/chat/completions`, header `Authorization: Bearer ${OPENROUTER_API_KEY}`.
- Model from `OPENROUTER_MODEL`, default `deepseek/deepseek-chat`. The only hard requirement is tool calling, since the loop depends on it. Note: `deepseek-r1`-style reasoning models have unreliable tool support and are not recommended.

## Output and Rendering

The model returns GitHub-flavored markdown. The server converts it to HTML with goldmark using the GFM extension in default safe configuration, so any raw HTML the model emits is escaped, not executed. Only the final answer is shown; the SQL and raw rows are not displayed.

There are no row caps anywhere. All rows a query returns are handed to the model so its answer reflects the full result. The only ceiling is the 30s statement timeout. Accepted consequence: a large-but-under-timeout result is resent in full on later turns and could eventually overflow the model context. Fine for a toy.

## Security

There is no authentication. The application is fully public and wide open by choice. The `ui` container binds to `127.0.0.1` only, so in any real deployment it must sit behind a reverse proxy (see DEPLOY.md); the protections below only keep the database itself safe, not access control.

Enforced:

- Query timeout: `SET LOCAL statement_timeout` to 30s, plus a 120s overall deadline on the whole request.
- Safe HTML: goldmark default config escapes raw HTML, so the model cannot inject scripts.
- Writes are impossible: `run_sql` executes inside a pgx read-only transaction (`pgx.TxOptions{AccessMode: pgx.ReadOnly}`), so INSERT/UPDATE/DELETE/DROP cannot run even if the model emits them. This is why no separate read-only role is needed.

Deliberately not covered (accepted): no authentication, no password, no rate limit, no usage cap.

## Chat Storage

One database account, one `public` schema. The text-to-SQL runs in a read-only transaction; no second role or connection string. Two tables hold saved chats alongside the game tables: `conversations` (id, title = first 50 chars of the opening prompt, created_at, updated_at) and `turns` (one row per API message, linked to a conversation, with role, content, tool_calls JSONB, and tool_call_id). Both are defined at the end of `sqlc/schema.sql`.

A `turns` row is one API message, not one question/answer exchange, because the full raw thread is persisted and resent. A single question typically produces several `turns` rows: the user prompt, an assistant message carrying a tool call (the SQL), a tool message carrying the rows, possibly another SQL/rows pair, then the final assistant answer.

Because `conversations`/`turns` live in `public`, re-applying `schema.sql` (which does `DROP SCHEMA public CASCADE`) also clears saved chats. Acceptable for a toy where reset is rare and chats are disposable.

## Request Flow (serve)

1. Receive `{conversationId, prompt}` (`conversationId` omitted for a new chat). The whole request runs under a 120s deadline.
2. If no `conversationId` is supplied, create the `conversations` row (the DB assigns its BIGSERIAL id via `RETURNING id`) with `title` = first 50 chars of the prompt, and return that id to the client. The conversation and its turns are persisted even if the question goes on to fail.
3. Load all `turns` for the conversation ordered by `id`, rebuild the API message array, and append the new user message. The full raw thread (all prior SQL tool calls and row results) is resent.
4. Run the agent loop. The first model step forces a tool call; after that it is free, up to 3 `run_sql` calls total. Each assistant and tool message is appended both to the live array and persisted as a `turns` row. Each `run_sql` runs in its own short read-only transaction with the 30s statement timeout; rows are serialized to JSON and returned as the tool result; a Postgres error is returned as the tool result so the model can self-correct.
5. The final assistant message is the markdown answer. Render it to HTML, persist it, bump `conversations.updated_at`, and return it. If the loop fails or the 120s deadline trips, the error is persisted and returned as the assistant message so it shows inline in the chat.

## API Endpoints

No authentication on any endpoint. The sidebar lists all conversations; there is no privacy between users.

```
GET  /api/conversations        -> [{id, title, updatedAt}]   (every conversation, newest first)

POST /api/ask                  {conversationId, prompt}      (conversationId omitted for a new chat)
                               -> {conversationId, title, html}

GET  /api/conversation?id=N    -> {id, title, exchanges:[{prompt, html}, ...]}
                               each user prompt paired with its final assistant answer

POST /api/conversation/delete  {id}
                               -> {ok}
```

The full raw thread (with tool calls and rows) is used internally for resend; the reopened-chat view shows only prompts and final answers.

## Frontend (Three Files)

Three vanilla files at the repo root, no framework, no CDN, embedded into the Go binary with `go:embed index.css index.html index.js` and served at `/`:

- `index.html`: a left `<aside class="sidebar">` (New Chat button plus the chat list) and a main `<main class="chat">` column. `index.js` is loaded as an ES module (`type="module"`).
- `index.css`: BEM-named blocks (`sidebar`, `conversation`, `chat`, `message`, `composer`) with element (`__`) and modifier (`--`) classes. Static singletons keep `id`s for JS hooks; styling is class-based.
- `index.js`: ES module, arrow functions throughout. Loads the conversation list (newest first, delete with a confirm), starts a new chat, loads a conversation, sends an ask, shows a thinking message during the wait, and renders an error inline as the assistant reply when a question fails. No browser-local storage; the request is blocking, no streaming.

The three files are linted and formatted with biome (`biome.json`, 2-space indent, recommended rules). The markdown-to-HTML step is server-side so the single JS file needs no markdown library.

## Dockerization

The CLI and the UI are the same Go binary built from the same image: the UI is `main -action serve`, the CLI is `main -action ingest|sample|statistics`. The CLI needs the Rust sidecar to parse replays, so `sc2json` is baked into the image.

```
+----------+-----------------------------------+----------------------------+
| Service  | What it runs                      | Lifecycle                  |
+----------+-----------------------------------+----------------------------+
| cli      | main -action ingest|sample|...    | on-demand (compose run)    |
| postgres | postgres:18.4                     | always up, healthchecked   |
| ui       | main -action serve                | always up, depends on db   |
+----------+-----------------------------------+----------------------------+
```

`ui` and `cli` build from the same image and bind-mount the repo at `/sources`. `cli` carries `profiles: ["cli"]` so `docker compose up` starts only `postgres` and `ui`.

Image (multi-stage Dockerfile):

```
Stage 1  rust:1-bookworm      -> cargo build --release  -> /sc2json (copied to /usr/local/bin/sc2json)
Stage 2  golang:1.26-bookworm -> installs air + sqlc, warms the module cache, sets WORKDIR /sources
```

There is no slim prebuilt-binary runtime stage. The image carries the Go toolchain, and the app is built from the mounted source at container start. `entrypoint.sh` switches on `ENVIRONMENT`:

- `development`: for the serve action it runs `air` (config `.air.toml`), which regenerates `models/` with sqlc, rebuilds the binary, and restarts on changes to `.go`, `.sql`, `.css`, `.html`, or `.js` files. Frontend files are watched because they are `go:embed`'d into the binary.
- `production` (and all one-shot cli actions): `sqlc generate`, `go build`, then exec the binary once.

The Rust sidecar is built once in stage 1; only the Go side rebuilds at runtime. `sc2json` lives at `/usr/local/bin/sc2json` and the Go binary finds it via the `SC2JSON` env var set in the image.

Postgres init: `sqlc/schema.sql` is mounted into the db container's `/docker-entrypoint-initdb.d/schema.sql`, run once on first boot of an empty data directory. The schema is a single file containing both the game tables and the chat tables.

Volumes: Postgres data is bind-mounted to `./postgres` on the host (persists chats and games; delete the directory to start fresh). `${REPLAYS_HOST}:/replays:ro` mounts the host replay directory read-only on the cli service. `REPLAYS` inside the container is fixed to `/replays`; the host path stays in `.env` as `REPLAYS_HOST` for Compose substitution.

Compose passes env directly via the `environment:` blocks; `.env` is read by Compose for `${VAR}` substitution, not copied into the image (godotenv's `Load()` no-ops when `.env` is absent, falling back to container env). Hostnames are service names (`postgres`). `ui` publishes `127.0.0.1:${PORT:-8080}:8080` so it is only reachable through a reverse proxy. `ui` and `cli` depend on `postgres` with `condition: service_healthy` (healthcheck = `pg_isready`). OpenRouter is the only outbound dependency.

## Locked Settings

- Access: no authentication, fully public, no rate limit or usage cap; `ui` binds to `127.0.0.1` and must be fronted by a reverse proxy.
- Actions: `ingest`, `serve`, `statistics`, `sample`. No precomputed reports.
- Chats: shared and public; the sidebar lists every conversation; conversation ids are BIGSERIAL; no browser-local storage.
- Conversation title: first 50 characters of the opening prompt.
- Containers: services named `postgres`, `ui`, `cli`; everything runs in Docker, source mounted at `/sources`.
- Environment: `ENVIRONMENT=development` runs the serve action under air (hot reload); `production` builds once and runs.
- Failures: failed chats are kept; the error shows inline as the assistant reply.
- History: full raw thread (all SQL tool calls and rows) resent every turn.
- Markdown to HTML: server-side (goldmark with GFM, safe mode).
- Model: `deepseek/deepseek-chat` by default, overridable via `OPENROUTER_MODEL`, must support tool calling.
- Output: rendered markdown answer only; no SQL shown in the UI.
- Postgres: `postgres:18.4`, data bind-mounted to `./postgres`.
- Query policy: at least one `run_sql` forced per question; cap of 3 `run_sql` calls per question. No row caps; the timeout is the only ceiling.
- sqlc: two files only, `sqlc/schema.sql` and `sqlc/queries.sql`; `models/` is generated, never committed.
- Statement timeout: 30 seconds per query; 120 second overall request deadline.
- Wait UX: blocking request with a loading spinner, no streaming.
