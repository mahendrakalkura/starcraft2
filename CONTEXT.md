# Context

Project context for LLM agents working on this codebase. README.md is the operator guide (build, configure, run). This file describes how the system is built and why decisions were made, plus the durable parsing and tooling facts learned while building it. It contains nothing about the actual game data or analysis findings; those are recomputed live from the database.

## Architecture

Two binaries plus Postgres.

- `main` (Go CLI and server, module `main`): orchestrates ingestion, runs analysis reports, and serves the web UI. Talks to Postgres via pgx/v5 and pgxpool. Queries are generated by sqlc into the `models/` package (gitignored, regenerated with `make sqlc`).
- `sc2json` (Rust sidecar, `sidecar/`): parses one .SC2Replay into compact JSON on stdout, built on s2protocol-rs. Stateless, one replay per invocation.
- Postgres: single account, single `public` schema, holds both the game tables and the chat tables.

`main` shells out to `sc2json` for parsing (default lookup: next to the `main` binary, override with `SC2JSON`). The Go side never parses the replay MPQ itself.

## Ingest Pipeline

`main -action ingest` walks the `REPLAYS` directories recursively for .SC2Replay files, skips any path already in the `files` table (any status, never retried), and runs the rest through a worker pool (`WORKERS`, default CPU count, CPU-bound). Each file ends in exactly one state:

- `duplicate`: a copy of an already-imported match. Matches are deduplicated by a SHA-256 fingerprint of played_at, map, and the team:name roster, so the same game saved under several paths is stored once.
- `failed`: the sidecar could not parse it. Delete the `files` row to retry.
- `imported`: parsed and stored in one transaction (game, players, messages, stats, units).
- `skipped_ai`: the game has a Computer participant; only player-vs-player games are stored.

Re-running ingest is cheap (already-processed paths are skipped without touching the replay). To re-import after a parser change, bump `PARSER_VERSION` in `sidecar/src/main.rs`, `make build`, and run `-action ingest -force`.

## Data Model

`files` records every path seen with its status and parser version. `games` (one per imported file, fingerprint-unique) -> `players` (team is a column; there is no teams table) -> `messages`, `stats`, `units` keyed by `player_id` and `tick` (game loop). The `matches` view joins winners and losers per game for reports.

Units semantics (the `action` column):

- `born`: units created instantly (trained, hatched), owned by the player.
- `init`: construction or warp-in starts (buildings, warped units), owned by the player. Cannons and other buildings only ever appear here.
- `killed`: credited to the killing player (a row means "kill by this player"). Deaths without a killer are not stored.

Engine helper units (for example InvisibleTargetDummy) are filtered out in the sidecar.

Durable facts needed to write correct SQL (full list under Replay Format and Parsing below): tick = 1/16 in-game second (960 per in-game minute); `tick / 16` lines up with `games.duration` (in-game seconds); PlayerStats arrive every 160 ticks; `food_used >= 195` means maxed; `food_used` and `food_made` are already real supply values.

## Replay Format and Parsing

- Tick = game loop. 16 loops per in-game second, 960 per in-game minute. `games.duration` is in-game seconds, so `tick / 16` lines up with duration. PlayerStats events arrive every 160 ticks (10 in-game seconds).
- `UnitBorn` = instantly created units (trained, hatched). `UnitInit` = construction/warp-in starts (all buildings, warpgate units). Both are needed: cannons and other buildings only ever appear as `UnitInit`. `UnitDied` carries `killer_player_id`; deaths without a killer (expired, suicide) are dropped by design.
- The game-end PlayerStats snapshot reuses the last periodic tick - the sidecar keeps the later event, or the stats PK `(player_id, tick)` would reject it.
- `InvisibleTargetDummy` (and other `*Dummy*` units) are engine helpers spawned per ability attack - thousands per game, born and instantly killed. Filtered in the sidecar; without the filter one player showed 15421 units instead of 1223.
- Lobby slot control values: Human = 2, Computer = 3 (AI players are named like "A.I. 2 (Hard)"). Participants have `observe = 0`.
- Player identity: details names embed clans as `&lt;CLAN&gt;<sp/>Name`; init-data has bare `name` + `clan_tag`, but with stray NUL bytes that must be stripped. MMR is init-data `scaled_rating`; APM/races/result/duration/version come from `replay.gamemetadata.json` (plain JSON in the MPQ, readable for any protocol version). Mode flags (`amm`, `competitive`) are in init-data game options.
- Tracker player_id maps to players via PlayerSetup events (player_id -> user_id + slot_id) and details `working_set_slot_id`. Never use lobby slot order (v1's attribution bug).
- s2protocol-rs falls back to the nearest known protocol for unknown base builds - parsed every replay from 2022 through build 96883 (2026) with zero errors. Blizzard's Python s2protocol and icza/s2prot stopped at protocol 95299 (Oct 2025) and fail on current replays.
- `food_used`/`food_made` are already divided by 4096 in s2protocol-rs (real supply values).
- gamemetadata races are 4-char codes (`Terr`, `Prot`, `Rand`); the sidecar normalizes to full names.

## Tooling Quirks

- sqlc (verified through v1.31.1) cannot propagate aggregate-alias columns out of CTEs ("column does not exist" / "table alias does not exist") and gets confused by unqualified `name` in multi-CTE queries ("column reference is ambiguous"). Workarounds: qualify columns (`players.name`), avoid referencing aggregate aliases across CTE boundaries - return per-row data and bucket in Go.
- A Go module named `main` cannot run `go test` (the test binary cannot import package "main"). Fine here since tests were removed by choice.
- Parser changes: bump `PARSER_VERSION` in `sidecar/src/main.rs`, `make build`, `./main -action ingest -force`. Full re-import of 5063 replays takes ~60-75s.

## Web UI: One Agentic Tool Loop

`main -action serve` starts a public web page where anyone can ask questions about the database in plain English and get a written answer. A browser cannot hold the OpenRouter key or open a Postgres connection on a public page, so the three static frontend files are served by the Go binary, which holds the key, talks to Postgres, and exposes a small JSON API. The "single HTML / JS / CSS" rule is about the frontend only; the server is the necessary fourth piece.

This is the Claude Code model, not a fixed pipeline. There is one conversation thread and the AI has exactly one tool: `run_sql(query)`.

1. The system prompt tells the model: you answer questions about this StarCraft 2 replay database, here is the schema, here are the domain rules, you have a `run_sql` tool, give your final answer in markdown.
2. The user asks a question.
3. The model emits a tool call: the SQL it wants to run.
4. The server executes it (read-only transaction, 30s statement timeout) and returns the rows to the model as the tool result.
5. The model reads the rows and either calls `run_sql` again (to fix an error or drill further) or writes its final markdown answer.
6. The server renders that answer to HTML and shows it.

What falls out of this design:

- Continuation is just chat. The conversation is a normal message list that we resend each turn.
- No separate summarizer. The same model that ran the query writes the answer in the same thread, so the answer is grounded in the rows it actually saw.
- Retry is automatic. If a query errors, the Postgres error comes back as the tool result and the model corrects itself and re-runs. No special retry code.

The model is forced to run at least one query per question (the first model step requires a tool call), so it can never answer a data question from memory. After that it is free to stop and answer or run more, up to a cap of 3 `run_sql` calls per question; past the cap it must answer with what it has or report that it could not. This stops both hallucinated-from-nothing answers and runaway loops.

## System Prompt

The system prompt is rebuilt on every call (not stored), so schema or rule changes take effect immediately, even in old chats. It embeds:

- The key durable domain facts the model needs to write correct SQL (see Replay Format and Parsing above): tick math, `food_used >= 195` means maxed, unit `action` semantics, team is a column (no teams table), the `matches` view, and the tracked PLAYERS.
- The schema, via `go:embed sqlc/schema.sql`. Only the game tables are described to the model. The `conversations` and `turns` tables are deliberately omitted from the schema text, so the model does not know they exist and will not query them.

Only durable facts go in. Precomputed analysis findings (win rates, map verdicts, anything stamped with an as-of date) are deliberately left out, so every answer is recomputed from live data instead of parroted from a frozen number. The prompt also tells the model to use Postgres `now()` and `current_date` for relative dates, so today's date never has to be injected.

Answer style (instructed in the prompt): answer-first and concise; use markdown tables whenever a query returns multiple rows; always cite the sample size ("over N games"); never speculate beyond the rows returned; and when a query returns nothing, say so plainly rather than inventing a reason.

## AI Provider and Model

- Provider is OpenRouter (OpenAI-compatible chat completions with tool calling), called over plain `net/http`. No SDK.
- Endpoint `https://openrouter.ai/api/v1/chat/completions`, header `Authorization: Bearer ${OPENROUTER_API_KEY}`.
- Model from `OPENROUTER_MODEL`, default `deepseek/deepseek-chat`. The only hard requirement is tool calling, since the loop depends on it. Note: `deepseek-r1`-style reasoning models have unreliable tool support and are not recommended.

## Output and Rendering

The model returns GitHub-flavored markdown. The server converts it to HTML with goldmark using the GFM extension in default safe configuration, so any raw HTML the model emits is escaped, not executed. Only the final answer is shown; the SQL and raw rows are not displayed. The markdown-to-HTML step is server-side specifically so the single JS file needs no markdown library.

There are no row caps anywhere. All rows a query returns are handed to the model so its answer reflects the full result. The only ceiling is the 30s statement timeout. Accepted consequence: a large-but-under-timeout result is resent in full on later turns and could eventually overflow the model context and error out. Fine for a toy.

## Security

There is no authentication. The application is fully public and wide open by choice; the protections below only keep the database itself safe, not access control.

Enforced:

- Query timeout: `SET LOCAL statement_timeout` to 30s, plus a 120s overall deadline on the whole request.
- Safe HTML: goldmark default config escapes raw HTML, so the model cannot inject scripts.
- Writes are impossible: `run_sql` executes inside a pgx read-only transaction (`pgx.TxOptions{AccessMode: pgx.ReadOnly}`), so INSERT/UPDATE/DELETE/DROP cannot run even if the model emits them. This is why no separate read-only role is needed.

Deliberately not covered (accepted): no authentication, no password, no rate limit, no usage cap. Anyone with the URL can fire unlimited prompts, each a paid AI call plus an arbitrary read of the game data. The model is not blocked from the `conversations`/`turns` tables at the database level; it is simply never told they exist.

## Chat Storage

One database account, one `public` schema. The text-to-SQL runs in a read-only transaction; no second role or connection string. Two tables hold saved chats alongside the game tables:

```sql
CREATE TABLE conversations (
    id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL,                  -- first 50 chars of the opening prompt
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE turns (
    id BIGSERIAL PRIMARY KEY,
    conversation_id BIGINT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    role TEXT NOT NULL,                   -- 'user' | 'assistant' | 'tool'
    content TEXT NOT NULL,                -- message text ('' for a pure tool-call assistant message)
    tool_calls JSONB,                     -- the SQL tool calls, when the assistant made them
    tool_call_id TEXT,                    -- links a tool result back to its call
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX turns_conversation_id ON turns(conversation_id, id);
```

A `turns` row is one API message, not one question/answer exchange, because the full raw thread is persisted and resent. A single question typically produces several `turns` rows: the user prompt, an assistant message carrying a tool call (the SQL), a tool message carrying the rows, possibly another SQL/rows pair, then the final assistant answer.

Because `conversations`/`turns` live in `public`, re-importing replays (which runs `schema.sql` and does `DROP SCHEMA public CASCADE`) also clears saved chats. The reset workflow in README recreates the chat tables empty afterward. Acceptable for a toy where reset is rare and chats are disposable.

## Request Flow (serve)

1. Receive `{conversationId, prompt}` (`conversationId` omitted for a new chat). The whole request runs under a 120s deadline.
2. If no `conversationId` is supplied, create the `conversations` row (the DB assigns its BIGSERIAL id via `RETURNING id`) with `title` = first 50 chars of the prompt, and return that id to the client. The conversation and its turns are persisted even if the question goes on to fail, so a failed first question still leaves a chat in the sidebar.
3. Load all `turns` for the conversation ordered by `id`, rebuild the API message array, and append the new user message. The full raw thread (all prior SQL tool calls and row results) is resent.
4. Run the agent loop. The first model step forces a tool call; after that it is free, up to 3 `run_sql` calls total. Each assistant and tool message is appended both to the live array and persisted as a `turns` row. Each `run_sql` runs in its own short read-only transaction (opened and closed around the single query) with the 30s statement timeout; rows are serialized to JSON and returned as the tool result; a Postgres error is returned as the tool result so the model can self-correct.
5. The final assistant message is the markdown answer. Render it to HTML, persist it, bump `conversations.updated_at`, and return it. If the loop fails or the 120s deadline trips, the error is persisted and returned as the assistant message so it shows inline in the chat.

## API Endpoints

No authentication on any endpoint. The sidebar lists all conversations; there is no privacy between users.

```
GET  /api/conversations        -> [{id, title, updatedAt}]   (every conversation, newest first)

POST /api/ask                  {conversationId, prompt}      (conversationId omitted for a new chat)
                               -> {conversationId, title, html}
                               creates the conversation if new (DB assigns the id), resends the
                               full thread, runs the agent loop, returns the rendered answer

GET  /api/conversation?id=N    -> {id, title, exchanges:[{prompt, html}, ...]}
                               the clean view for rendering a reopened chat: each user prompt
                               paired with its final assistant answer, intermediate tool messages omitted

POST /api/conversation/delete  {id}
                               -> {ok}
```

The full raw thread (with tool calls and rows) is used internally for resend; the reopened-chat view shows only prompts and final answers.

## Frontend (Three Files)

Three vanilla files at the repo root, no framework, no CDN, embedded into the Go binary with `go:embed index.css index.html index.js` and served at `/`:

- `index.css`: traditional CSS for the sidebar, chat exchanges, the form, and the rendered markdown (tables, code, lists).
- `index.html`: a left `<aside>` sidebar (New Chat button plus the chat list) and a main chat column (scrollback of prompt and answer, plus a prompt box).
- `index.js`: loads the conversation list (newest first, delete with a confirm), starts a new chat (no id until the server assigns one on the first ask), load-conversation, send-ask, a loading spinner during the wait, and inline rendering of an error as the assistant reply when a question fails. No browser-local storage. The request is blocking, no streaming.

## Dockerization

The CLI and the UI are the same Go binary: the UI is `main -action serve`, the CLI is `main -action ingest|versus|...`. The CLI needs the Rust sidecar to parse replays. So there is one app image (Go binary plus sidecar) used by two services.

```
+---------+------------------------------------------+----------------------------+
| Service | What it runs                             | Lifecycle                  |
+---------+------------------------------------------+----------------------------+
| cli     | main -action <ingest|report|...>         | on-demand (compose run)    |
| db      | postgres:18.4                            | always up, healthchecked   |
| web     | main -action serve  (the UI server)      | always up, depends on db   |
+---------+------------------------------------------+----------------------------+
```

`web` and `cli` build from the same image. `cli` carries `profiles: ["cli"]` so `docker compose up` starts only `db` and `web`.

Image (multi-stage Dockerfile):

```
Stage 1  rust:1-bookworm      -> cargo build --release  -> /sc2json
Stage 2  golang:1.26-bookworm -> CGO_ENABLED=0 go build -> /main   (index.* is go:embed'd into the binary)
Stage 3  debian:bookworm-slim -> copy /main + /sc2json side by side, plus ca-certificates for OpenRouter egress
```

- Both binaries land in the same directory so the default sidecar lookup (next to `main`) works for the CLI.
- `CGO_ENABLED=0` keeps the Go binary static (pgx is pure Go). The Rust binary glibc-links, so the runtime base is `debian-slim`, not alpine. Dependency layers are cached before copying source.
- `.dockerignore` excludes `sidecar/target/`, `.git`, the committed `main` and `sc2json` binaries, `.env`, and `*.db`, so the build always compiles fresh.

Database init scripts are mounted into Postgres's `/docker-entrypoint-initdb.d/`, run once on first boot of an empty data volume, in alphabetical order:

```
sqlc/schema.sql        -> 01-schema.sql   (canonical game schema, reused, no duplication)
sqlc/chat_schema.sql   -> 02-chat.sql     (conversations and turns, reused, no duplication)
```

Volumes: a named `pgdata` volume holds Postgres data (persists chats and imported games); `${REPLAYS_HOST}:/replays:ro` mounts the host replay directory read-only, only on the cli service. `REPLAYS` inside the container becomes `/replays`; the host path stays in `.env` as `REPLAYS_HOST` for Compose substitution.

Compose passes env directly; the Go app's `godotenv.Load()` no-ops when `.env` is absent, falling back to container env, so no code change is needed. Hostnames become service names (`db`). `web` publishes `8080:8080`. `web` and `cli` use `depends_on: db` with `condition: service_healthy` (healthcheck = `pg_isready`). OpenRouter is the only outbound dependency.

## Locked Settings

- Access: no authentication, fully public, no rate limit or usage cap.
- Chats: shared and public; the sidebar lists every conversation for everyone; conversation ids are BIGSERIAL; no browser-local storage.
- Conversation title: first 50 characters of the opening prompt.
- Failures: failed chats are kept; the error shows inline as the assistant reply.
- History: full raw thread (all SQL tool calls and rows) resent every turn.
- Markdown to HTML: server-side (goldmark with GFM, safe mode).
- Model: `deepseek/deepseek-chat` by default, overridable via `OPENROUTER_MODEL`, must support tool calling.
- Output: rendered markdown answer only; no SQL shown in the UI.
- Postgres: `postgres:18.4`.
- Query policy: at least one `run_sql` forced per question; cap of 3 `run_sql` calls per question. No row caps; the timeout is the only ceiling.
- Statement timeout: 30 seconds per query; 120 second overall request deadline.
- Wait UX: blocking request with a loading spinner, no streaming.
